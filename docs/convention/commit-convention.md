# Commit Convention

코히어의 커밋 작성 규칙을 바탕으로 [Conventional Commits 1.0.0](https://www.conventionalcommits.org/ko/v1.0.0/) 형식을 따른다.
한국어 요약, 길이 제한, 허용 타입 목록은 바톤 프로젝트의 추가 규칙이다.

연계 문서: [브랜치 컨벤션](./branch-convention.md), [협업 컨벤션](./collaboration-convention.md)

## 1. 목적

커밋 메시지만으로 변경의 종류, 범위, 이유를 파악하고 관련 이슈와 PR을 찾을 수 있게 한다.
하나의 커밋에는 하나의 논리적 변경을 담는다.

## 2. 기본 형식

```text
<type>(<scope>): <subject>

<body — 선택>

<footer — 선택>
```

`scope`는 선택이다. 생략하면 `docs: 커밋 컨벤션 작성`처럼 작성한다.

| 요소 | 필수 | 규칙 |
| --- | --- | --- |
| `type` | O | 아래 허용 목록의 영어 소문자 타입 사용 |
| `scope` | X | 영향받는 도메인이나 모듈. 예: `auth`, `user`, `config` |
| `subject` | O | 한국어 요약, 50자 이내, 끝에 마침표 없음 |
| `body` | X | 변경 이유와 필요한 맥락. 한 줄 72자 내 줄바꿈 권장 |
| `footer` | X | 이슈 참조 `Refs: #12`, 호환성 변경 설명 `BREAKING CHANGE:` 등 |

50자 제한은 `type(scope): `를 제외한 요약 부분에 적용한다.
제목과 본문, 본문과 footer 사이에는 빈 줄을 둔다. 본문이 없으면 제목과 footer 사이에 빈 줄을 둔다.

### 요약 작성 규칙

- 무엇을 바꿨는지 구체적으로 쓴다.
- `추가`, `수정`, `제거`, `개선`처럼 명사형으로 끝낸다.
- `버그 수정`, `update`, `wip`처럼 변경을 알 수 없는 요약은 피한다.

| 좋은 예 | 피할 예 |
| --- | --- |
| `feat(auth): 로그인 API 추가` | `feat: 기능 추가` |
| `fix(user): 이메일 중복 검사 오류 수정` | `fix: 버그수정` |
| `docs: 커밋 컨벤션 작성` | `docs: 문서를 작성했습니다.` |

## 3. 허용 타입

코히어와 동일한 11개 타입을 사용한다. 이 목록은 프로젝트에서 선택한 규칙이며,
Conventional Commits가 모든 타입을 필수로 요구하는 것은 아니다.

| 타입 | 용도 |
| --- | --- |
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서만 변경 |
| `style` | 포맷, 공백 등 코드 동작에 영향을 주지 않는 변경 |
| `refactor` | 동작을 유지하면서 코드 구조 개선 |
| `perf` | 성능 개선 |
| `test` | 테스트 추가 또는 수정 |
| `build` | 빌드 시스템 또는 외부 의존성 변경 |
| `ci` | GitHub Actions 등 CI/CD 설정과 스크립트 변경 |
| `chore` | 다른 타입에 해당하지 않는 유지보수 |
| `revert` | 이전 커밋 되돌리기 |

브랜치 타입과 커밋 타입은 별개다. 예를 들어 `feature/12-login-api` 브랜치에서도
기능 구현은 `feat`, 테스트 추가는 `test`, 문서 수정은 `docs`로 기록할 수 있다.

## 4. 본문과 이슈 참조

본문은 단순한 변경 목록보다 변경이 필요한 이유를 중심으로 작성한다.
커밋 footer에서는 `Refs: #번호`로 관련 이슈를 참조한다.

```text
fix(user): 이메일 중복 검사 오류 수정

이메일 앞뒤 공백 때문에 중복 검사를 통과하는 문제를 막기 위해
검사 전에 입력값을 정규화한다.

Refs: #12
```

이슈 종료는 개발 PR 본문의 `Closes #번호`로 연결한다.
원본 저장소의 기본 브랜치를 `develop`으로 설정하고, 해당 브랜치에 PR을 병합할 때 이슈가 종료되도록 운영한다.
커밋에는 종료 키워드 대신 `Refs:`를 사용한다.
자세한 조건은 [협업 컨벤션](./collaboration-convention.md)과 [GitHub 이슈 연결 안내](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)를 참고한다.

## 5. 호환성이 깨지는 변경

기존 앱이나 웹이 사용하던 API를 그대로 호출할 수 없게 되는 변경은 반드시 표시한다.
예를 들어 필수 응답 필드를 삭제하거나 입력 형식을 바꾸는 경우가 해당한다.

다음 방법 중 하나 이상을 사용한다.

1. 타입 또는 scope 뒤, 콜론 앞에 `!`를 붙인다.
2. footer에 `BREAKING CHANGE:`와 변경 내용을 작성한다.

```text
refactor(user)!: 응답 필드 userId를 id로 변경

BREAKING CHANGE: 사용자 응답의 userId 필드를 id로 변경한다.
앱과 웹의 응답 파싱 코드를 함께 수정해야 한다.

Refs: #24
```

호환성 변경 표시는 타입과 관계없이 적용한다.
Squash 병합 시에도 최종 커밋에서 이 표시와 설명이 유지되는지 확인한다.

## 6. 커밋 단위

- 하나의 커밋에는 하나의 논리적 변경만 담는다.
- 관련 없는 기능, 리팩토링, 전체 포맷팅을 한 커밋에 섞지 않는다.
- 기능과 그 기능을 검증하는 테스트는 하나의 논리적 변경으로 함께 커밋할 수 있다.
- 동작과 무관한 포맷팅은 로직 변경과 분리한다.
- 작업 중 남긴 임시 커밋은 병합 전에 정리한다. Squash 최종 메시지는 반드시 이 문서의 형식을 따른다.
- `revert` 커밋은 되돌리는 이유와 원래 커밋의 식별자를 본문 또는 footer에 남긴다.
- 비밀값, 인증 토큰, 개인정보를 커밋 메시지에 넣지 않는다.

## 7. 배포 버전과의 관계

커밋 규칙과 배포 버전 번호는 구분한다.
현재 배포 버전 번호의 증가 방식과 자동 버전 산정 도구는 정하지 않았다.
따라서 `feat`, `fix`, `perf`를 작성했다고 버전이 자동으로 증가한다고 가정하지 않는다.

향후 [SemVer](https://semver.org/lang/ko/) 기반 배포 정책을 정할 때 버전 증가 기준을 별도로 문서화한다.
초기 `0.x` 단계에서도 호환성이 깨지는 변경은 계속 표시한다.

## 체크리스트

- [ ] 허용된 타입과 기본 형식을 사용했다.
- [ ] 한국어 요약이 50자 이내이며 마침표 없이 구체적으로 작성되었다.
- [ ] 필요한 경우 본문에 변경 이유를 적었다.
- [ ] 관련 이슈를 `Refs: #번호`로 참조했다.
- [ ] 호환성이 깨지는 변경에 `!` 또는 `BREAKING CHANGE:`를 표시했다.
- [ ] 하나의 커밋이 하나의 논리적 변경을 담는다.
- [ ] 메시지에 비밀값이나 개인정보가 없다.
